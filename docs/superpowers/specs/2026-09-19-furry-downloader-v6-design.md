# FurryDownloader v6 设计规格

## 1. 目标

本次迭代把现有“输入一个画师后下载一次”的工具升级为可持续更新的画师订阅式下载器：

1. 用户可以维护一个画师列表，点击一次“更新列表”后依次下载列表中所有画师的全部 `gallery` 和 `scraps` 最新作品。
2. 重复更新时跳过已经下载的图片，并对同一图片 URL 做持久化去重。
3. 每个作品的描述文字保存为独立 UTF-8 文本文件，放在画师目录下的 `descriptions` 子目录。
4. 使用现代浏览器完成 FA 登录，通过浏览器 Cookie 管理器取得登录 Cookie，并将 Cookie 传递给详情页和图片下载请求。
5. 保持 `master` 分支不变，所有实现放在 `codex/furry-downloader-v6` 分支，并按功能拆分提交。

## 2. 非目标

- 本次不重写下载线程池，不增加代理池、账号池或并发调度系统。
- 本次不做图片内容哈希去重；持久化 URL 索引是主要去重依据，已有文件检查作为兼容和恢复机制。
- 本次不改变 FA 账号登录流程本身，不保存用户名或密码，只保存登录后 Cookie。
- 本次不保证绕过 FA 的验证码或站点风控；用户仍需在嵌入式浏览器中完成站点要求的验证。

## 3. 已知现状与约束

- 当前项目是旧式非 SDK C# WinForms 项目，目标框架为 .NET Framework 4.0。
- 现有 `FaLogin` 使用 IE 内核 `WebBrowser`，通过 WinInet 的 `InternetGetCookieEx` 读取 Cookie；检测方式依赖 Cookie 字符串中出现 `; a=`，顺序变化时会失效。
- 当前 `DownloadManager` 的图片请求没有传入主窗体保存的 Cookie，因此即使登录成功，受保护图片也无法稳定下载。
- 作品详情页已经被请求一次以解析原图地址，描述文字可以在同一次页面请求中提取。
- 当前页面使用 `submission-description-text` 作为作品描述正文容器；正文包含 HTML 换行和实体，需要转换为纯文本。
- 直接用当前 .NET SDK 构建原项目时，旧 `.resx` 资源会触发 `GenerateResourceUsePreserializedResources` / `System.Resources.Extensions` 错误，因此构建兼容性需要在本分支一并处理。

## 4. 推荐架构

### 4.1 领域模型与持久化

新增以下小型、可独立测试的组件：

- `ArtistEntry`：画师名和是否启用。画师名以规范化后的 FA 用户名保存。
- `ArtistListStore`：负责读写 `我的文档\FaDownloader\artists.xml`，使用 `XDocument`，文件不存在时返回空列表；保存时采用临时文件替换，避免程序中断造成 XML 损坏。
- `DownloadIndex`：负责读写 `我的文档\FaDownloader\download-index.xml`，记录规范化图片 URL 与本地文件路径。读取失败时返回空索引并在日志中提示，不阻止已有文件继续使用。
- `SubmissionInfo`：表示一个作品详情页解析结果，包含详情页 URL、作品 ID、图片 URL、图片文件名和描述文本。

XML 采用稳定、人工可读的结构。画师列表只保存画师名；下载索引只保存去重所需的 URL 和相对路径，不保存页面 HTML。

### 4.2 解析层

扩展 `Analyze`：

- 从详情页一次性解析 `SubmissionInfo`。
- 继续支持现有下载链接格式，兼容 `//d.facdn.net/...` 和完整 `https://...` URL。
- 从 `submission-description-text` 节点取正文；将 `<br>`、`<br />` 转为换行，去除剩余 HTML 标签，使用 `WebUtility.HtmlDecode` 解码实体，并保留有意义的空行。
- 解析不到图片 URL 时抛出当前下载流程能够识别的异常；描述缺失时保存空文本而不是阻止图片下载。

### 4.3 下载流程

将现有单画师流程抽出为“处理一个画师”的内部方法，UI 对外只提供“更新列表”这一项批量动作：

1. 顺序更新 `gallery`，再更新 `scraps`。
2. 每页请求统一带当前 Cookie；识别用户不存在、需要登录、网络错误和正常结束。
3. 每个详情页只请求一次，得到图片 URL 和描述。
4. 先查 `DownloadIndex`，再检查目标文件是否存在：
   - 已登记且目标文件存在：跳过图片下载，但刷新对应描述文件。
   - 目标文件存在但索引没有记录：登记后跳过图片下载。
   - 两者都不存在：加入现有 `DownloadManager` 下载队列，并在成功回调中写入索引。
5. 描述文件使用图片文件名去掉原扩展名后加 `.txt`；默认保存到 `<画师目录>\descriptions\`。如果两个来源产生同名图片，使用作品 ID 作为描述文件名后缀保证不覆盖。
6. 同一轮更新过程中维护内存 URL 集合，避免同 URL 被重复加入队列；持久化索引在图片成功写入后更新。
7. 点击“更新列表”时按 XML 中的列表顺序串行处理全部画师，画师内部沿用已有下载线程池；停止按钮会停止新增详情任务并等待已入队任务结束。列表中任意画师失败时记录失败并继续处理后续画师，最后汇总成功、失败和跳过数量。

### 4.4 用户界面

在现有主窗体上增加画师列表区，不删除原有高级下载参数：

- `ListBox` 显示已保存画师。
- “添加”使用当前画师输入框，去除首尾空格和下划线，按不区分大小写去重。
- “删除”删除选中画师并立即保存列表。
- “更新列表”按列表顺序更新所有画师；列表为空时显示明确提示。
- 更新期间冻结列表编辑和更新按钮，只保留停止按钮。
- 日志显示画师、分类、页数、跳过数量、图片完成数和描述保存结果。

单个画师的下载目录继续使用用户选择的根目录和画师名组合，gallery 保持现有扁平布局，scraps 保持 `scraps` 子目录布局，以兼容已有下载结果。

### 4.5 登录与 Cookie

将 `FaLogin` 的 IE `WebBrowser` 替换为 WebView2 控件：

- 项目目标框架升级到 .NET Framework 4.8。
- 引入 `Microsoft.Web.WebView2` 包，并在初始化时使用每个应用固定的用户数据目录，保证登录状态可跨次使用。
- 页面加载完成后从 `CoreWebView2.CookieManager.GetCookiesAsync("https://www.furaffinity.net/")` 获取 Cookie。
- 以 Cookie 名称解析身份 Cookie，至少要求 `a` 存在且值非空；不依赖 Cookie 的排列顺序或分号前后的空格。
- 登录窗口只有在身份 Cookie 获取成功后才关闭；用户取消或关闭窗口时返回空结果。
- 如果 WebView2 Runtime 不存在，显示安装提示和检测失败原因，不再静默返回空 Cookie。
- Cookie 文件仍与现有版本兼容，保存位置不变；下载请求统一通过任务对象传递 Cookie，包括详情页和图片请求。

## 5. 错误处理与安全边界

- 所有网络请求继续使用现有重试机制；登录失效时停止当前画师更新，日志提示重新登录，不把登录页面误当作作品页面。
- XML 文件损坏时备份原文件为 `.bak` 后从空列表/空索引启动，并在日志中报告；不删除用户的图片。
- 文件名继续经过安全清理，禁止详情页内容产生路径分隔符或 `..` 路径。
- Cookie 只写入现有用户文档目录，不输出完整 Cookie 到日志；登录调试日志只能记录是否获得身份 Cookie。
- WebView2 用户数据目录放在 `我的文档\FaDownloader\WebView2`，关闭窗口时释放控件。

## 6. 测试策略

先建立可执行的纯逻辑测试项目，再写生产实现。测试覆盖：

1. 画师名规范化、大小写不敏感去重、XML 保存和重新加载。
2. 图片 URL 规范化、索引命中、文件存在但索引缺失、重复 URL 不重复排队。
3. 详情页解析：图片链接、`http`/`https`/协议相对链接、描述换行、HTML 实体、缺失描述和恶意标签。
4. 描述文件路径生成和文件名安全清理。
5. Cookie 字符串由 Cookie 集合生成，以及身份 Cookie 顺序变化时仍能识别登录成功。
6. 旧缓存和已有图片继续可用。

无法在无图形桌面环境中自动验证 WebView2 的真实登录和 Turnstile，将通过启动检查、CookieManager 适配层单元测试，以及最终人工验收验证。

## 7. 验收标准

- 可以添加至少两个画师，关闭并重新打开程序后列表仍存在。
- 点击“更新列表”可以按列表顺序完整遍历所有画师的 gallery 和 scraps，重复点击时已有图片不重复下载。
- 每个成功处理的作品都有对应的 UTF-8 描述文本，描述内容可读且换行正常。
- 登录成功后能获得身份 Cookie；需要登录的画师页面和图片请求不再因为未带 Cookie 失败。
- 没有 WebView2 Runtime 时给出明确提示。
- 自动化测试全部通过；Release 构建成功；`master` 无改动，feature 分支提交历史清晰。
